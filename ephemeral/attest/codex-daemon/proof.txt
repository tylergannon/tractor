Proof for issue #143 (commit 2 of 2, fixing round-01 review findings): the
codex adapter attaches to the machine's one shared `codex app-server`
daemon, reuses one WebSocket connection across every session and turn, and
recovers from a dead connection by resuming every thread it knows about
before handing the new connection to any caller.

Model used: gpt-5.6-luna (Codex), the cheapest Codex model, for every turn
in both the attest program and the live test below.

## Finding 1 fix: a redialed connection now re-subscribes existing threads

`adapter.conn` (codex/codex.go) now calls a new `resumeThreads` before
handing out a freshly dialed connection: for every session the adapter
knows about, it sends `thread/resume` with the same params the old
per-process adapter used (`threadId`, `cwd`, `approvalPolicy: "never"`,
`sandbox: "danger-full-access"`), checks the returned thread id matches,
and registers the thread for routing on the new connection. If any resume
fails, `conn(ctx)` returns that error rather than handing back a
half-subscribed connection. `turn/start` alone was never enough: only
`thread/start`, `thread/fork`, and `thread/resume` add the calling
connection to a thread's subscriber set in the daemon.

## Commit 2: HarnessAdapter.Close, called for real when a scope ends

Model used: gpt-5.6-luna (Codex), for the turn in the live test below.

`HarnessAdapter` now has a required `Close(ctx, sessionID) error` method.
`scope.end` (gimble/scope.go) calls it for every adopted session that has a
native id, on a `context.WithTimeout(context.Background(), 10*time.Second)`
independent of the run's own ctx, and records `SessionClosed{Error}`
either way. A session with no native id (never ran a turn) gets no Close
call. Close failures never enter the scope's own error; they are pushed
onto the run under a mutex and Run joins the aggregate as a new `*CloseError`
into its returned error, alongside `RunEnded.Error`, once the root scope has
ended.

The Codex adapter's `Close` (codex/codex.go) removes the session from
`a.sessions`, deregisters the thread from the shared connection's routing
table (`connection.unregisterThread`, the counterpart to `registerThread`)
whether or not that connection is still alive, and then sends
`thread/archive {"threadId": id}` over a live connection: the shared one if
its reader is healthy, otherwise a redial through the same path turns use,
because a dead client socket does not mean the daemon or the thread is
gone. The redial for Close never starts a daemon: if `daemon version`
reports it stopped, the thread holds nothing anywhere and Close returns
nil without a call (`TestCloseNeverStartsAStoppedDaemon` proves this with
a fake `codex` on PATH). It never stops or restarts the daemon. An unknown
id (never registered, or already closed) returns nil without a network
call, and the daemon's "no rollout found" answer for a thread someone else
already archived is treated as success.

Why archive rather than unsubscribe: the first version of this commit used
`thread/unsubscribe`, and the live run showed both threads still in
`thread/loaded/list` afterwards. A loaded thread keeps its MCP child
processes and their pipes inside the shared daemon. Measured on this
machine on 2026-09-12: archiving one thread dropped the daemon from 261 to
249 open descriptors and from 48 to 45 child processes; archiving the
day's 12 proof threads dropped it from 248 to 141 descriptors and from 45
to 19 children, and from 18 loaded threads to the 7 that belong to Codex
Desktop. The daemon runs under a 256-descriptor soft limit and had logged
413 "Too many open files" errors by then. Unsubscribe releases nothing
that matters; archive is the release.

### Using an archived thread again: not through the adapter

Probed 2026-09-13 against the daemon (codex-cli 0.153.4): `thread/read`
works on an archived thread, but `thread/resume` and `thread/fork` answer
`session <id> is archived. Run codex unarchive <id> to unarchive it first`.
After `thread/unarchive` both work. The first version of this change had the
adapter unarchive and retry, and its live test passed while leaving one
extra thread loaded per run. Stepping through the sequence on a raw
connection, tracking `thread/loaded/list` after each call:

    new loaded after unarchive: [01a09a4d-d6f6-78e0-a66e-27366843943f]
    fork returned: 01a09a4d-d9ae-76a1-af96-e222bd7864bb
    new loaded after fork (beyond unarchive): [01a09a4d-d9ae-76a1-af96-e222bd7864bb]
      01a09a4d-d6f6-... path=<nil> forkedFromId=<nil> status=map[type:active]
      archive 01a09a4d-d6f6-... err: no rollout found for thread id ...
    ghosts left from this probe: [01a09a4d-d6f6-78e0-a66e-27366843943f]

`thread/unarchive` itself creates a ghost: a new in-memory thread with no
rollout, not the unarchived thread, which the daemon then refuses to
archive (`no rollout found`), delete (`thread is not persisted and cannot
be deleted`), or resume. `codex unarchive <id>` on the CLI does the same:

    new loaded after CLI unarchive: [01a09a4e-78dc-7aa3-b51a-df8e69452666]
    ghosts left from this probe: [01a09a4e-78dc-7aa3-b51a-df8e69452666]

The fork after either unarchive is clean and archivable; only the
unarchive leaks. Ghosts stay loaded until the daemon restarts. Six were
created on this machine while finding this (hand probes and three runs of
the unarchive-and-retry test) and are recorded here so they are not
mistaken for adapter leaks:

    GHOST 01a09a46-d4e5-7c40-8c02-29f4930695f3
    GHOST 01a09a48-854b-7862-8e43-a3f8b30748cf
    GHOST 01a09a49-1fc7-7df0-9492-ce7b41f16622
    GHOST 01a09a4c-9684-7722-9940-36bb9df78941
    GHOST 01a09a4d-d6f6-78e0-a66e-27366843943f
    GHOST 01a09a4e-78dc-7aa3-b51a-df8e69452666

Decision: the adapter does not unarchive. `callThread` (codex/codex.go)
reads the thread first (`thread/read`, read-only; an archived thread's
`path` is under `archived_sessions`) and a fork or resume of an archived
thread is `errThreadArchived`, with no fork, resume, or unarchive call
after that read. The error says why rather than telling the caller to
unarchive, since unarchiving by any route is what leaks. A closed
session's thread cannot be reused until the daemon's unarchive stops
leaking; nothing in Gimble's API reaches a closed session today, so this
only constrains a future feature.

On daemon start: the adapter starts the daemon when `daemon version`
reports none running, for turns and session creation. That is the
intended design (attach to the one daemon if it exists, otherwise start
it, never stop it). Only Close declines to start one, because a stopped
daemon holds nothing to release.
`TestForkOfAnArchivedParentFailsWithoutAGhost` archives a parent out from
under the adapter, forks it, and asserts the error, that Close still ran
for the parent, and that `thread/loaded/list` gained nothing.

### What was left out and why

- The unsubscribe version of this commit was what pushed the shared daemon
  into `Too many open files (os error 24)`: each proof run left its
  threads loaded, and by the end of the day the daemon held 261
  descriptors against a 256 soft limit. That is the failure issue #143
  exists to prevent, reproduced by the first attempt at fixing it. The
  archive version above is the correction. Idempotence (`Close` on an
  unknown id, twice) is proven without any daemon traffic in
  `codex/codex_test.go`'s `TestCloseIsIdempotentForAnUnknownSession`, and
  correspondingly for Claude in `claude/claude_test.go`.
- Every other acceptance item (the scope-error/CloseError contract, the
  cancelled-run close-with-fresh-context guarantee, the no-native-id case,
  and `Complete.RecordingError`'s independence from close failures) is
  proven with a fake adapter in the root package's `issue143_test.go`,
  which needs no live daemon.
